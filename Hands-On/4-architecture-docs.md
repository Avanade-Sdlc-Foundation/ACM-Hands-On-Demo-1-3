# 演習 4: カスタムプロンプトを使用したアーキテクチャドキュメントの生成

| [← 前の手順](./3-comparison.md) | [次の手順: 技術的負債改善計画 →](./5-tech-debt.md) |
|:--|--:|

カスタムアーキテクチャプロンプトを活用して、Spring Boot PetClinicプロジェクトの包括的なアーキテクチャドキュメントを生成します。このドキュメントは、新規メンバーのオンボーディング、設計決定の記録、および将来の拡張計画に活用できます。

## シナリオ

プロジェクトマネージャーから、以下の要求がありました：
- 新しいチームメンバーが迅速にプロジェクトを理解できるアーキテクチャ文書が必要
- ステークホルダーへの技術説明資料として活用可能な図表が必要
- システムの技術的依存関係と制約事項を明確に文書化したい
- 将来的なスケーラビリティ検討のための現状把握資料が必要

これらの要求を満たすため、GitHub Copilotの専用アーキテクチャプロンプトを使用して、包括的で実用的なドキュメントを生成します。

## ? 必須 1. アーキテクチャドキュメント生成の準備

### 1.1 新しいChatセッションの開始

1. Copilot Chatの新しいセッションを開始します
   - 右上の「＋」アイコンまたは「New Session」をクリック
   ![New Session](images/new-session.png)
2. クリーンな分析環境であることを確認します
3. プロジェクト全体が認識されていることを確認します

### 1.2 プロジェクト状態の確認

1. 主要なアーキテクチャファイルの存在を確認：
   - `PetClinicApplication.java` (メインクラス)
   - `application.properties` (設定ファイル)
   - `pom.xml` または `build.gradle` (依存関係)
   - データベース設定ファイル群

## ? 必須 2. 包括的アーキテクチャドキュメントの生成

### 2.1 メインアーキテクチャプロンプトの実行

Copilot Chatに以下のプロンプトを入力して実行します：

```
/architecture-blueprint-generator

このSpring Boot PetClinicプロジェクトの包括的なアーキテクチャドキュメントを生成してください。

含めるべき要素：
- 技術スタック分析（Spring Boot 3.5.0、Java 17、JPA、Thymeleaf）
- C4図（System、Container、Component レベル）
- ドメインモデル（Owner、Pet、Vet、Visit の関係性）
- データアーキテクチャ（H2/MySQL/PostgreSQL対応）
- セキュリティ考慮事項
- 品質属性と実装パターン
- デプロイメント戦略（Docker、Kubernetes対応）
```

### 2.2 生成プロセスの観測

1. Copilotがプロジェクト全体を分析している過程を観察します
2. 複数のファイルタイプを横断した分析が実行されることを確認します
3. 生成には数分かかる場合があります（包括的分析のため）

## ? 必須 3. 生成されたドキュメントの内容確認

### 3.1 技術スタック分析の確認

生成されたドキュメントで以下の技術情報が含まれていることを確認します：

**フロントエンド技術:**
- Thymeleaf テンプレートエンジン
- Bootstrap CSS フレームワーク
- 静的リソースの構成

**バックエンド技術:**
- Spring Boot 3.x
- Spring Data JPA
- Spring MVC
- Bean Validation

**データベース対応:**
- H2 Database (開発/テスト)
- MySQL (本番環境オプション)
- PostgreSQL (本番環境オプション)

### 3.2 C4アーキテクチャ図の確認

以下のレベルの図が含まれていることを確認します：

1. **System Context Level** (レベル1):
   - エンドユーザー
   - PetClinicシステム
   - 外部データベース

2. **Container Level** (レベル2):
   - Webアプリケーション
   - データベースコンテナ

3. **Component Level** (レベル3):
   - Controller層
   - Service層
   - Repository層
   - Domain Model

### 3.3 ドメインモデルの関係性確認

以下のエンティティ関係が正確に表現されていることを確認します：

```
Owner (1) ←→ (0..n) Pet
Pet (n) ←→ (1) PetType
Pet (1) ←→ (0..n) Visit
Visit (n) ←→ (1) Vet
```

## ? 参考 4. ドキュメント品質の詳細評価

### 4.1 アーキテクチャ決定記録（ADR）の確認

生成されたドキュメントに以下のアーキテクチャ決定が記録されているか確認：

1. **フレームワーク選択理由**
   - Spring Boot採用の根拠
   - Thymeleaf選択の理由

2. **データアクセス戦略**
   - JPA/Hibernate使用理由
   - Repository パターン採用根拠

3. **セキュリティアプローチ**
   - 認証・認可戦略
   - データ保護方針

### 4.2 非機能要件の記載確認

以下の品質属性が適切に記載されているか確認：

- **パフォーマンス**: 応答時間、スループット
- **可用性**: アップタイム要件
- **スケーラビリティ**: 拡張性考慮事項
- **保守性**: コード品質、テスト戦略

## ? オプション 5. ドキュメントの拡張と改善

### 5.1 追加分析の実行

より詳細な分析が必要な場合、以下のような追加プロンプトを実行：

```
生成されたアーキテクチャドキュメントに以下の詳細を追加してください：

- API エンドポイント一覧と仕様
- データベーススキーマの詳細設計
- エラーハンドリング戦略
- ログ出力とモニタリング方針
- 本番環境デプロイメント手順
```

### 5.2 図表の改善

```
以下の図表も追加生成してください：

- システム間通信フロー図
- データフロー図（DFD）
- シーケンス図（主要ユースケース）
- デプロイメント図
```

## ? 必須 6. ドキュメントの保存と整理

### 6.1 生成ファイルの保存

1. 生成された内容を `Project_Architecture_Blueprint.md` として保存します
2. プロジェクトルートまたは `docs/` フォルダに配置します
3. 適切な命名規則とフォルダ構成を確認します

### 6.2 図表ファイルの管理

1. 生成された図表があるかを確認します
2. Mermaid形式やPlantUML形式で記述されている場合は、別途レンダリング環境を準備
3. 画像ファイルとして出力可能であれば `images/` フォルダに保存

## ?? トラブルシューティング

### 問題が発生した場合

1. **アーキテクチャプロンプトが認識されない場合**
   - `/architecture-blueprint-generator` コマンドの正確性を確認
   - Copilot Chatの最新版使用を確認
   - VS Codeの再起動を試行

2. **生成内容が不十分な場合**
   - プロジェクトの主要ファイルがすべて存在するか確認
   - 段階的に細分化したプロンプトでの追加生成
   - 特定の領域に焦点を当てた再分析の実行

3. **図表が生成されない場合**
   - テキストベースの説明から手動で図表作成を検討
   - 外部ツール（Draw.io、Lucidchartなど）の活用

### パフォーマンス改善

大規模プロジェクトの場合：
```
プロジェクトのメインパッケージ（org.springframework.samples.petclinic）に絞って
アーキテクチャ分析を実行してください
```

## まとめと次のステップ

この演習で以下を実現しました：

- **包括的アーキテクチャドキュメントの自動生成**
- **技術スタックの詳細分析と文書化**
- **C4モデルに基づいた階層的アーキテクチャ図の生成**
- **ドメインモデルと関係性の明確化**
- **非機能要件と品質属性の文書化**

生成されたアーキテクチャドキュメントは以下の用途で活用できます：
- 新規メンバーのオンボーディング資料
- ステークホルダーへの技術説明資料
- 将来的なシステム拡張の検討材料
- 技術監査や品質評価の基礎資料

次のステップでは、技術的負債の改善計画を作成し、現在のシステムの課題点と改善方法を体系的に整理します。これにより、アーキテクチャドキュメントと合わせて完全なプロジェクト技術文書セットが完成します。
